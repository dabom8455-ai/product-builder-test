# ⑤ 시스템·데이터 인프라 (클부장 직속)

> **한 줄 임무:** 사업의 뼈대를 세우고 수익을 현실화하는 **모든 과정을 데이터로 남긴다.**
> 흩어진 정보를 하나의 진실(Single Source of Truth)로 모아, 4개 팀이 그 위에 선다.

이 축은 팀이 아니라 **바닥**이다. 4개 팀이 만들고 파는 모든 활동이 여기에 기록되고,
그 기록이 다시 자동화·판매·개선의 연료가 된다. **당분간 클부장이 직접 관장**하고,
데이터량이 사람 손을 넘어서는 시점에 정식 팀으로 승격한다.

---

## 1. 왜 이 축이 존재하는가

> "과정이 데이터로 남지 않으면, 우리는 매번 처음부터 다시 시작하는 회사가 된다."

- **자동화의 전제:** 기록이 없으면 자동화할 대상도, 기준도 없다.
- **판매의 증거:** 우리 학원의 데이터(절감 시간·전환율·수익)가 곧 상품의 세일즈 포인트다.
- **개선의 근거:** 무엇이 먹혔는지 데이터로 봐야 다음 판단이 선다. (감이 아니라 근거)
- **선순환의 계기판:** 돈이 어디서 들어오고 어디로 새는지 실시간으로 보여야 재투자를 결정한다.

---

## 2. 핵심 원칙

1. **모든 과정은 기록된다** — 리드 유입부터 매출 발생, 의사결정까지 전부 한 줄의 데이터로.
2. **단일 진실(SSOT)** — 같은 정보를 두 곳에 따로 적지 않는다. 한 곳이 원본, 나머지는 참조.
3. **작게 시작, 표준은 처음부터** — 도구는 단순하게(노션/시트) 시작하되, 항목(스키마)은 처음부터 표준화.
4. **재사용 가능하게** — 우리 학원용 데이터 구조가 그대로 판매 상품의 구조가 되도록 설계.

---

## 3. 데이터 모델 — 우리가 남겨야 할 것 (도메인별)

각 도메인은 "한 건이 생길 때마다 한 줄(레코드)"로 쌓인다.

| 도메인 | 무엇을 남기나 (핵심 필드) | 주 생성 팀 |
|--------|--------------------------|-----------|
| **① 리드(Lead)** | 유입경로·연락처·아이나이·문의내용·유입일·상태 | ②마케팅 |
| **② 상담(Consultation)** | 리드연결·상담일시·방식·결과(등록/보류/이탈)·메모 | ①운영 |
| **③ 원생(Student)** | 이름·등록일·과정·담당·상태(재원/휴원/퇴원) | ①운영 |
| **④ 출결(Attendance)** | 원생·일자·등하원시각·출결상태 | ①운영 |
| **⑤ 레슨·진도(Lesson)** | 원생·일자·교재·진도내용·다음목표 | ①운영 |
| **⑥ 수강료·결제(Billing)** | 원생·청구월·금액·납부상태·납부일 | ①운영/③수익화 |
| **⑦ 매출·비용(Finance)** | 항목·구분(매출/비용)·금액·일자·분류 | ③수익화 |
| **⑧ 콘텐츠(Content)** | 채널·주제·발행일·성과(도달/유입) | ②마케팅 |
| **⑨ 지식상품(Product)** | 전자책/시스템·가격·판매채널·판매수·매출 | ③④ |
| **⑩ 자동화 모듈(Module)** | 모듈명·대상업무·자동화단계(L0~L2)·검증여부 | 전 팀 |
| **⑪ 의사결정·실험(Decision Log)** | 날짜·안건·결정·근거·결과 | 클부장 |
| **⑫ 문서 레지스트리(Doc Registry)** | 문서명·GitHub경로·노션링크·최종수정 | 클부장(sync-docs) |

> ⑪ **의사결정 로그**가 핵심입니다. "왜 이렇게 결정했는가"가 남아야 대표님의 통찰이 축적됩니다.
> ⑫ 문서 레지스트리는 이미 `sync-docs` 스킬의 `notion-map.json`이 그 시작입니다.

## 4. 데이터 흐름 (한 바퀴 = 선순환)

```
②리드 → ①상담 → ①원생등록 → ④출결/⑤진도 → ⑥수강료 → ⑦매출
   ▲                                                        │
   └──── ⑧콘텐츠·⑨지식상품(②③④) ←── ⑦수익 재투자 ←────────┘
                       (모든 단계가 ⑤인프라에 기록)
```

## 5. 세부업무 분할 (L0 → L2)

### 5-1. 데이터 저장소 구축
- 🔨 진행 `[L0]` **핵심 도메인 테이블 정의** — 3개 도메인(리드·상담·의사결정) 필드 확정, 나머지 9개 대기
- 🔨 진행 `[L0]` **저장소 선택·개설** — 노션 DB 3종 개설 완료(①리드·②상담·⑪의사결정), 9종 대기 → [`docs/infra/data_registry.md`](../infra/data_registry.md)
- ✅ 완료 `[L0]` **입력 규칙 표준화** — 3개 DB 상태값·날짜·연결 규칙 확정 (레지스트리 문서)

### 5-2. 수집 자동화 (팀 산출물 → 데이터)
- ⬜ 대기 `[L0]` **리드 자동 적재** — 홈페이지 상담폼 → ①리드 테이블 자동 기록
- ⬜ 대기 `[L1]` **출결·진도 연결** — ①운영팀 자동화 산출물 → ④⑤ 테이블 연동
- ⬜ 대기 `[L1]` **재무 자동 집계** — ⑥⑦ 데이터 → ③수익화팀 손익 대시보드

### 5-3. 인프라 표준·연결
- ✅ 완료 `[L1]` **문서 레지스트리(sync-docs)** — GitHub↔노션 문서 동기화 (구축 완료)
- ✅ 완료 `[L0]` **의사결정 로그 개설** — 노션 DB 개설 + 첫 결정 3건 기록 완료
- ⬜ 대기 `[L1]` **대시보드** — 핵심지표(North Star)를 한 화면에서 보기

---

## 6. 기술 로드맵 (작게 시작 → 확장)

1. **1단계(지금):** 노션 데이터베이스 + 구글 시트. 사람이 입력하되 항목은 표준화.
2. **2단계:** 홈페이지 폼·자동화 도구에서 데이터가 자동 적재.
3. **3단계:** 통합 대시보드 + (필요 시) 실제 DB. 이 구조를 그대로 상품으로 포장.

> 원칙: 1단계에서도 **스키마(항목 구조)는 3단계를 염두에 두고** 설계한다. 그래야 갈아엎지 않는다.

---

## 7. 산출물

- 표준화된 **데이터 저장소**(모든 팀 공용) → 전 팀
- **핵심지표 대시보드** → 대표·클부장
- **의사결정 로그** → 대표(통찰 축적)
- 재사용 가능한 **데이터 구조 자체** → 판매 상품의 뼈대

## 8. KPI

- 데이터로 기록되는 도메인 수 (12개 중 몇 개 가동)
- 자동 적재 비율(수기 입력 → 자동 수집 전환율)
- 대시보드로 즉시 확인 가능한 핵심지표 수

## 9. 1차 실행 항목 (이번 주 물길)

> 👉 **12개 도메인 중 지금 당장 필요한 3개부터 노션 DB로 개설한다:**
> **① 리드 · ② 상담 · ⑪ 의사결정 로그.**
> 홈페이지 상담폼이 붙는 즉시 리드가 쌓일 곳이 있어야 하고, 상담 결과가 남아야 전환율이 보이며,
> 의사결정 로그는 오늘부터 대표님의 판단을 자산으로 쌓기 시작한다.
> — *클부장 직접 관장. 저장소 개설 후 각 팀에 입력 규칙 배포.*
